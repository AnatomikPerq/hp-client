# Roadmap

Открытые проблемы и идеи HYPER CLIENT. Каждый пункт: что не так или чего
хотим, что уже выяснено в коде и как это делать. Что сделано, отсюда
убирается; история остаётся в git.

Состояние на 17.10.2026, версия 0.1.0-beta.5 (сборка `5b536a5` с
исправлениями minewire установлена владельцем, но номер версии не поднят).

## Открытые проблемы

### minewire падает молча, интерфейс этого не видит

17.10 minewire перестал пропускать трафик при включённом VPN: интерфейс
показывал «подключено», приложение нейросети не работало. Сервер через час
был здоров: 11-минутный тест движка в тот же вечер (запрос каждые 5 с) прошёл
без единого сбоя, медиана ~170 мс. Сбой временный, и разобрать его задним
числом нельзя: логов нет ни одного.

- Приложение не следит за движками после запуска: `MinewireRuntime` ждёт
  `connected` только при подключении. Движок, потерявший сессию, сам
  переподключается, а UI об этом не знает.
- Подвисшее TCP-соединение (провайдер «замораживает» поток, пакеты
  пропадают молча) движок замечает только по keepalive yamux: до ~45 с без
  трафика, потом переподключение. Если блокировка повторяется, цикл
  повторяется.
- Логов нет: `ygLogger` в релизе ничего не пишет, движок пишет в stderr
  GUI-процесса (в никуда), логи Xray по умолчанию выключены.

Сделать:
- писать предупреждения движков в `run/minewire.log` (с ротацией) и вести
  файл журнала приложения в релизе, хотя бы для ошибок подключения;
- фоновый контроль здоровья: состояние движков (`minewireState`) и
  периодическая живая проверка (`LivePingProbe`); при сбое показывать
  «нет связи» в интерфейсе и трее, уведомлять;
- по желанию: при «Автоматически» переключаться на следующий живой узел.
  Сейчас автопереключения нет совсем: умерший узел так и остаётся.

Это же основа для kill switch (см. идеи).

### Утечка мимо VPN при живой смене узла

Балансировщик `proxy` в конфиге имеет `fallbackTag: direct`. При смене
узла во время подключения `LiveControl` сначала удаляет старый выход, потом
добавляет новый. В эти миллисекунды соединения, идущие через балансировщик
(DNS Xray через туннель, DoT 853, GitHub в умном режиме), уходят напрямую,
в TUN — с реального IP. Остальной трафик в этом окне сбрасывается, а не
утекает. Исправить: убрать `fallbackTag: direct` (fail closed) или менять
теги так, чтобы новый выход добавлялся раньше удаления старого.

### Гонка записи на сервере minewire

У сервера автора (v26.7.3) та же ошибка, что была в клиенте: кадр уходит
несколькими `Write`, а таймер keepalive/времени пишет в тот же сокет
параллельно с данными. Под тяжёлой загрузкой кадры могут перемешаться и
сессия зависнет; однобайтовые TCP-сегменты к тому же заметны для DPI.
Клиент исправлен в `libXray/third_party/minewire-cli`; серверу нужен тот же
патч (собрать, заменить бинарник на VPS, предложить PR автору).

### Иероглифы в подсказке значка в трее

Причина не в кодировке. `tray_manager` 0.5.3 не инициализирует
`NOTIFYICONDATA nid`, и первый `setIcon` берёт из неё подсказку: это
случайные байты, которые Windows рисует как иероглифы. На Windows мы
`setToolTip` не вызываем (только на macOS,
`lib/service/shared/menu/tray/service.dart`). Исправление: вызывать
`setToolTip` и на Windows сразу после `setIcon`. Можно заодно показывать
в подсказке состояние: «HYPER CLIENT · подключено · узел». Плагину стоит
отправить исправление (обнулять `nid` в конструкторе).

### Меню трея не закрывается кликом мимо

Windows закрывает меню из трея по клику мимо, только если окно-владелец
было активным до `TrackPopupMenu`. `tray_manager` делает его активным лишь
при `bringAppToFront: true`, а мы вызываем `popUpContextMenu()` без
параметров. Исправление: передавать `bringAppToFront: true` на Windows
(параметр помечен устаревшим, нужен `ignore`). Проверить, что открытое окно
приложения при этом не выпрыгивает поверх других некстати. Если выпрыгивает,
патчить плагин: `SetForegroundWindow` + `PostMessage(WM_NULL)` по
документации Microsoft.

### Задержка minewire под нагрузкой

Под параллельной закачкой пинг через minewire растёт до 1–2 с: клиент
разрешает серверу до 16 МБ в полёте на поток (`MaxStreamWindowSize`), и
интерактивные запросы ждут в общей очереди одного TCP. Подобрать окно
(1–2 МБ хватает на ~300 Мбит/с при 50 мс) и замерить на стенде.

### Мелочи

- Сборка с исправлениями minewire называется beta.5. После проверки TUN
  выпустить beta.6 с релизом на GitHub.
- TUN с minewire после исправлений вживую не проверен (это делает
  владелец: на его машине тесты TUN запрещены).
- Смена узла между minewire и обычным узлом перезапускает ядро (у них разный
  DNS), в TUN это лишний запрос UAC.

## Решено не делать

- **UDP через minewire.** Это изменение протокола; к тому же UDP внутри
  одного TCP даёт рывки при потерях. Для UDP есть Hysteria2.

## Идеи

### 1. Kill switch для прокси и TUN

Цель: если VPN упал, трафик не идёт в обычный интернет.

Режим прокси. Сейчас при неожиданном выходе ядра приложение возвращает
прежние настройки прокси, и программы уходят напрямую. Kill switch здесь
дешёвый: оставлять системный прокси указывающим на мёртвый порт (запросы
падают, а не утекают) и громко уведомлять. Программы, которые системный
прокси игнорируют, в этом режиме не удержать ничем.

Режим TUN. Когда ядро падает, маршруты wintun исчезают и всё идёт
напрямую. Настоящий kill switch на Windows — фильтры Windows Filtering
Platform: запретить исходящее всем, кроме loopback, локальной сети (по
настройке), процесса ядра и адресов серверов. Готовая реализация есть в
WireGuard for Windows (`tunnel/firewall`, MIT, Go). Фильтры должны
переживать падение ядра, значит их ставит и снимает повышенный процесс,
а снять их после сбоя — отдельное действие с UAC.

Важно: 17.10 ядро было живо, умер движок minewire, и соединения просто
падали. Утечки там, скорее всего, не было, была невидимая поломка (см.
проблему выше). Kill switch и контроль здоровья нужны оба.

Оценка: режим прокси — малая задача; TUN через WFP — большая.

### 2. Раздельный туннель по приложениям и доменам, профили

Xray-ядро уже умеет правила по процессам (`"process": [...]`, на Windows
процесс ищется по таблице соединений), в нашей модели правил этого поля
пока нет. Готовые категории доменов уже лежат в GeoData: `OPENAI`,
`ANTHROPIC`, `CATEGORY-AI-!CN`, `GOOGLE-GEMINI`, `PERPLEXITY`, `XAI`,
`DISCORD`, `YOUTUBE`, `TELEGRAM`, `SPOTIFY`, `TWITCH`, `STEAM` и другие.

Профиль = набор процессов + категорий доменов + режим («только это через
VPN» или «всё, кроме этого»). Готовые профили: «Нейросети», «Discord»,
«YouTube», «Мессенджеры», «Игры».

Где обычно ломается у других клиентов и что продумать:
- дочерние процессы (у Electron-приложений и Discord их несколько,
  плюс отдельный апдейтер) — профиль должен знать их все;
- UDP (голос Discord) — поиск процесса для UDP-потоков;
- DNS: запросы на Windows делает системная служба, а не само приложение.
  Маршрутизировать надо по SNI/sniffing и процессу, а не по DNS; FakeDNS
  помогает;
- в режиме прокси по процессам работает только для программ, которые
  ходят через системный прокси (проверить, видит ли Xray процесс у
  loopback-подключения).

Оценка: ядро готово; работа — модель правил, компилятор, экран выбора
приложений и профилей. Средне-крупная задача, но реальная.

### 3. AmneziaWG

В Xray есть WireGuard, но без обфускации Amnezia (нет магических
заголовков H1–H4, паддингов S1/S2, пакетов I1–I5); маски `noise` их не
заменяют. Путь — как у minewire: встроить `amneziawg-go` (MIT) в libXray
с пользовательским сетевым стеком (netstack) и локальным SOCKS5, к
которому Xray ходит как к обычному socks. В этом SOCKS можно сделать и UDP:
это наш локальный код, протокол не меняется. Работает и на мобильных.

Нужно: разбор конфигов AWG (`.conf`, ссылки Amnezia) в Dart до libXray,
импорт из подписки (сейчас такой узел, похоже, при импорте теряется —
посмотреть формат в подписке владельца), пинг через временный движок.

Оценка: средне-крупная.

### 4. vk-turn-proxy

[cacggghp/vk-turn-proxy](https://github.com/cacggghp/vk-turn-proxy)
(Go, GPL-3.0, совместима с нашей лицензией) заворачивает UDP WireGuard или
Hysteria в DTLS 1.2 и гонит через TURN-серверы звонков VK на свой VPS.
Нужен там, где пропускают только «белые» сервисы. Сервер у владельца уже
стоит.

Встраивание: клиент — это `package main` (~68 КБ) с обработкой капчи VK
(слайдер и ручная), его придётся вынести в библиотеку внутри libXray. Он
даёт локальный UDP-порт, на который идёт WireGuard-выход Xray (или
AmneziaWG из пункта 3). «Тонкая поддержка» в интерфейсе: ссылка на звонок,
адрес сервера, число потоков, TCP или UDP до TURN, диалог капчи.

Риски: VK меняет API и капчу, ссылки на звонки живут, пока звонок не
завершён. Оценка: крупная; логично после пункта 3.

### 5. Трей

Обе причины найдены (см. «Открытые проблемы»). Оценка: час вместе с
проверкой.

### 6. Отчёт о сети для разработчиков протоколов

Клиент собирает картину сети пользователя в файл, который тот сам
отправляет автору протокола:

- DNS: системный, DoH и TCP-ответы для тестовых доменов, подмены;
- TCP/TLS: соединение, RST, блокировка по SNI (тот же IP с разными SNI),
  «заморозка» потока после ~16 КБ к зарубежным адресам;
- UDP/QUIC: проходит ли вообще, есть ли ограничение;
- скорость до известных CDN, MTU, IPv6;
- рукопожатия своих узлов по протоколам (VLESS Reality, Hysteria2,
  WG/AWG, minewire, TURN): что проходит и что режется;
- вывод: что сработало бы для обхода.

Приватность: IP маскируется до сети и ASN, без паролей, UUID и адресов
своих серверов (или они хешируются), явное согласие, отправка только
вручную. Близкий по духу проект — OONI Probe, но он не проверяет
протоколы обхода.

Оценка: средняя; начать с части проверок и наращивать. Многие проверки
переиспользуют пинги и движки из пунктов 2–4.

## Порядок, который предлагаю

1. Быстро: трей; утечка при смене узла; после проверки TUN — релиз beta.6.
2. Контроль здоровья, уведомления, журналы — прямо про случай 17.10.
3. Kill switch: сначала режим прокси, потом TUN через WFP.
4. Раздельный туннель с профилями.
5. AmneziaWG, затем vk-turn-proxy поверх него.
6. Отчёт о сети, по частям.
