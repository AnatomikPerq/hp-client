# Roadmap

Открытые проблемы и идеи HYPER CLIENT. Каждый пункт: что не так или чего
хотим, что уже выяснено в коде и как это делать. Что сделано, отсюда
убирается; история остаётся в git.

Состояние на 24.10.2026. Выпущена 0.1.0-beta.9: ядро Xray v26.10.21 на
Go 1.27.3 (срочное обновление Xray: из встроенных корней убраны три
скомпрометированных), апстрим по #238 (ручные группы серверов, DNS по
умолчанию для Raw и конфигов провайдера, подсказки XDrive/MASQUE/XDNS в
редакторе JSON, новый пул FakeDNS IPv6), анимированная кнопка подключения
без всплывающей подсказки, проверка связи и монитор здоровья меряют VPN во
всех режимах. Предыдущая, beta.8 (22.10), принесла kill switch, профили
маршрутизации и режим «Выборочно», конфиги провайдера Remnawave и
«Подключено» только после старта Xray.

## Решения владельца

- **Апстрим #220–#231 слит 21.10.2026** (решение того же дня: сначала
  аккуратно влить апстрим, потом свои профили маршрутизации). Режим
  «конфиг провайдера целиком» оставлен на выбор пользователя: он включается
  в подписке (панель Remnawave или режим «Конфигурация провайдера»), по
  умолчанию JSON-подписки дают обычные узлы. Идея владельца — показывать
  его приоритетным пунктом во вкладке маршрутизации; не сделано.
- **Профили маршрутизации сделаны 21.10.2026** (идея 2). Решения того дня:
  профили — переключатели поверх режима, их правила важнее правил режима;
  новый режим «Выборочно» пускает через VPN только то, что названо во
  включённых профилях, остальное напрямую; список «заблокировано в России»
  — файл runetfreedom, вшитый в сборку, а включение профиля обновляет его
  без скачивания всего файла; есть и готовые профили (с программами), и
  до пяти своих. Названия профилей не утверждены. Устройство — в
  `CLAUDE.md`, «Traffic profiles and Selective mode».
- **Апстрим #236–#238 слит 24.10.2026.** Ручные группы серверов —
  разделы внутри карточки «Добавленные вручную», а не отдельные карточки
  (выбор владельца из двух вариантов): карточка сохраняет свою кнопку
  «Использовать» на все ручные серверы, группы только раскладывают список.
  Устройство — в `CLAUDE.md`, «UI layout».
- **Отчёт о сети, первая часть, 25.10.2026** (идея 5). Решения того дня:
  вход из «Настройки → Диагностика» (там же «Данные отчёта»), на главной
  ссылка «Проверить сеть», когда связи нет; экран — карточка с выводом
  («подойдёт / не подойдёт / также найдено») и сворачиваемые разделы;
  отдаётся текстом для мессенджера и файлом JSON, ссылка на просмотр на
  сайте — потом. zapret — в последнюю очередь и по возможности без его
  запуска. Устройство — в `CLAUDE.md`, «Network report».
- **Свой DNS ядра — DNS сети, 25.10.2026**: имена узлов и прямые
  соединения ядро разрешает через DNS физического интерфейса (на Android
  — сети под VPN), а если он молчит — через 1.1.1.1. Раньше брался DNS
  туннеля (8.8.8.8), дома у владельца четверть таких запросов терялась
  («TUN на хосте 22.10»). В живую: ядро в виртуалке с мёртвым DNS сети
  поднимается и разрешает имена; дома у владельца в TUN — не проверено.
- **Обновление по кнопке и сборка Android, 25.10.2026** — то, что
  выпускает клиент из беты в 1.0. Решения того дня: обновление скачивается
  по нажатию «Обновить» (с прогрессом), проверяется по SHA-256 из GitHub и
  ставится с одним UAC, приложение перезапускается и переподключается;
  у Android свой `applicationId` `io.github.anatomikperq.hyperclient`, свой
  ключ подписи (хранится вне репозитория, копию держит владелец), APK по
  ABI в релизах GitHub; проверки — эмулятор на диске D, потом телефон
  владельца. Цель — Android не хуже Windows. Устройство — в `CLAUDE.md`,
  «Android» и «One-click update». Проверено в виртуалке: beta.8 в TUN
  скачала установщик, после UAC закрылась, установщик дождался её выхода
  (9 с), поставил beta.9 и запустил её, та переподключилась. В режиме TUN
  это второй запрос UAC — уже для ядра; без службы его не убрать.
- **vk-turn-proxy откладывается** (идея 4): не делаем и не планируем, пока
  владелец не вернётся к нему сам.

## Открытые проблемы

### Сводка открытых вопросов (24.10.2026)

Подробности — в разделах ниже; здесь всё, что осталось после beta.9.

- **TUN без интернета в «Выборочно»** (хост владельца, 22.10): собственный
  DNS ядра (8.8.8.8, новый UDP-сокет на каждый запрос) теряет четверть
  запросов, и прямые соединения ждут по 5–10 секунд. См. «TUN на хосте
  22.10». (Проверка связи с beta.9 меряет VPN, а не прямой путь.)
- **Медленный первый старт ядра.** Первое подключение после запуска
  приложения в виртуалке ждёт Xray около 30 секунд (раз было 2 минуты),
  повторные — 2–4 секунды. Теперь это честное «Подключение…», но причина не
  найдена: время уходит внутри ядра до конца `RunXray` (kill switch, DNS
  интерфейса, загрузка geodata или создание адаптера). Часы сеанса на
  главной считают и это ожидание.
- **Первое соединение сразу после «Подключено»** один раз не прошло
  (следующие — да): похоже, Windows ещё доводит маршруты нового адаптера.
- **Промахи поиска программы** в TUN (IPv4 и IPv6): соединение уходит мимо
  своего профиля, в «Выборочно» — напрямую. Причина не найдена.
- **Kill switch:** снятие блокировки при входе в Windows, если ядро упало,
  а приложение не стоит в автозапуске (сейчас — только следующий запуск
  приложения); должны ли правила брандмауэра Windows действовать на ядро
  (разрешения kill switch сейчас сильнее); TUN на Linux без защиты; режим
  «Блокировать без VPN» ждёт решения владельца; подписки не обновляются,
  пока блокировка держится.
- **Не проверено:** быстрый запуск Windows и IPv6 (в виртуалке их не
  воспроизвести); kill switch и режим системного прокси на конфиге
  провайдера, «Скопировать в личный Raw», частичный импорт подписки (#229);
  INCY и другие провайдеры, кроме HYPER VPN и своей панели.
- **Подписки:** обновление подписки, у которой поменялся выбранный узел,
  перезапускает ядро с UAC вместо живой смены; одно обновление
  JSON-подписки шло 6,5 минуты (повтор — 4 секунды, не воспроизвелось);
  для конфига провайдера `app.log` пишет «connected: tunnel» без имени.
- **Профили маршрутизации:** резервная копия их не переносит; имена
  программ сравниваются с учётом регистра; голос Discord ловится только
  правилом программы; на Android/iOS только домены и адреса; названия
  профилей не утверждены.
- **Интерфейс:** на экране 1024×768 диалоги добавления и изменения
  подписки не помещаются (кнопку видно только после прокрутки); первое
  включение раздачи в LAN вызывает запрос брандмауэра Windows (правило
  установщиком не добавляется).
- **Тихие установка и удаление** при запущенном приложении теперь
  завершаются с кодом 1: для администраторов, которые ставят программу
  удалённо, это стоит описать.
- Dart доверяет не только корневому хранилищу Windows, но и хранилищу
  промежуточных сертификатов (`CA`) — так устроен Dart, у нас это лишь
  объясняло, почему ошибка Let's Encrypt видна не всем.

### Android: что осталось после первой сборки (25.10)

Проверено на эмуляторе Android 16 (x86_64) с подпиской HYPER VPN:
импорт по ссылке `hyperclient://`, пинг всех типов узлов (и minewire),
подключение через AWG 3.1, REALITY + XHTTP, XHTTP с TLS и minewire с
«Проверкой связи», живая смена узла без перезапуска, отчёт о сети при
включённом VPN (показывает домашнего провайдера, а не узел), ссылка на
системный kill switch, обновление из приложения с beta.8 на beta.9 с
возвратом VPN после замены пакета и при отмене установки.

Осталось:
- **телефон владельца**: arm64-сборка на настоящем устройстве и сети;
- **программы в профилях маршрутизации** на Android работают только как
  домены и адреса. В libXray и Xray-core уже есть поиск владельца
  соединения по UID (`RegisterProcessFinder`, `getConnectionOwnerUid`);
  нужно регистрировать его в `:native`, переводить выбранные приложения
  в UID при подготовке подключения и выбирать приложения в редакторе
  профиля;
- «Нет связи» от монитора здоровья на Android в живую не проверено
  (на эмуляторе без root узел не отрезать);
- CI Android не собирает (только локально, ключ подписи вне CI);
- один раз ссылка `hyperclient://`, пришедшая во время запроса разрешения
  на VPN, оставила бесконечную загрузку (запрос не показался); после
  перезапуска приложения всё работало;
- экран первичной настройки апстрима пишет «по умолчанию — материковый
  Китай» (это и на Windows).

### minewire: что осталось после контроля здоровья

Случай 17.10 (движок потерял сессию, интерфейс показывал «подключено») теперь
виден: `ConnectionHealthMonitor` раз в 30 с проверяет путь системного трафика
и состояние движков, после трёх неудач показывает «Нет связи» на главной и в
трее и шлёт уведомление; `minewireState` честно сообщает `connected: false`,
когда сессия оборвалась; в `run/app.log` и `run/minewire.log` остаётся след.

Осталось:
- автопереключение при «Автоматически»: умерший узел так и остаётся. С #220
  в настройках умного режима и своих маршрутов есть стратегия `leastPing`
  (observatory по 1–3 узлам, выбранным при подключении; новые соединения
  уходят на живой). Осталось: когда умерли все выбранные, подставлять
  следующий узел из списка живой сменой по сигналу монитора здоровья;
- подвисшее TCP-соединение движок замечает только по keepalive yamux (до
  ~45 с); можно сократить `KeepAliveInterval`, но это лишний трафик.

### Kill switch: что осталось

Сделан 21.10.2026 (решения владельца: включён по умолчанию, блокировка
держится до конца сеанса Windows, строгий режим — отдельная настройка).
Устройство и ловушки — в `CLAUDE.md`, «Kill switch».

Проверено в тестовой виртуалке 21.10.2026 (TUN, релизная сборка): падение
ядра (`Stop-Process -Force`) закрывает интернет и DNS, локальная сеть
(SSH) работает, на главной «Интернет заблокирован»; «Снять блокировку» без
UAC; переподключение под блокировкой, в том числе на узел minewire с
доменом и с «набором номера сервера» (bootstrap DNS ядра проходит); выход
из сеанса при живом ядре снимает блокировку (`WM_ENDSESSION`); падение и
выход из сеанса — блокировка остаётся в новом сеансе, пока не запустится
приложение, а оно снимает её («kill switch from an earlier session
lifted»); строгий режим переживает перезагрузку, приложение держит его и
снимает без UAC; удаление программы во время блокировки возвращает сеть.

Осталось:
- **быстрый запуск** («Завершение работы» с гибернацией ядра) в этой
  виртуалке не воспроизвести: встроенное ПО Hyper-V не даёт гибернацию;
  нужна машина, где она есть;
- **IPv6** при выключенном IPv6 в приложении: в виртуалке на `Ethernet`
  IPv6 не привязан, как у владельца, проверить нечем;
- после падения ядра выход из Windows **не** снимает лёгкую блокировку:
  её снимет только следующий запуск приложения. 22.10 исправлен текст
  настройки (он обещал снятие при выходе); снимать блокировку при входе
  без запуска приложения пока не стали;
- разрешающие фильтры kill switch для ядра сильнее правил брандмауэра
  Windows: исходящее правило «блокировать адрес» на ядро не действует
  (заметил, пытаясь отрезать узел для проверки `leastPing`);
- удаление и обновление поверх работающего приложения оставляли его файлы
  до перезагрузки — и тихие из другого сеанса, и обычное удаление в своём
  (Restart Manager его не закрывает: окно только прячется в трей). Исправлено
  22.10: приложение держит мьютекс, а установщик и деинсталлятор (`AppMutex`)
  просят сначала выйти из него, так что VPN отключается и системный прокси
  возвращается штатно. Проверено в виртуалке: обычное удаление показывает
  «HYPER CLIENT is currently running», тихое из другого сеанса завершается
  с кодом 1 и ничего не трогает. Принудительно закрывать приложение не
  стали: в режиме прокси это оставило бы системный прокси на мёртвом порту;
- TUN на Linux не защищён (нужны правила nftables от ядра); режим прокси
  на Linux удерживается так же, как на Windows;
- режим «Блокировать интернет без VPN» (блок и после «Отключить», как
  lockdown у Mullvad) — не делали, ждёт решения владельца;
- до переподключения после сбоя во время блокировки приложение не может
  обновить подписки (их имена разрешает системная служба DNS, она
  заблокирована); пинг узлов и minewire работают.

### Апстрим #220–#231: что не проверено

Слит 21.10.2026 (см. «Слияние апстрима приложения»). Автоматические тесты
и анализатор проходят; в тот же день релизная сборка проверена в тестовой
виртуалке. Что проверено и что нет:

**Remnawave** проверен 21–22.10 на своей тестовой панели 3.4.5 (Docker на
хосте, перед ней Caddy с тестовым CA, порты открыты только на адрес Default
Switch для виртуалки) и ноде (Xray 26.7.28). Профиль ядра на пять входов:
VLESS REALITY Vision, VLESS XHTTP REALITY, Trojan gRPC REALITY, VLESS WS с
mux у хоста, Shadowsocks; шаблон Xray JSON с раздельным DNS, блокировкой
рекламы и правилами-метками (один домен в блок, несколько напрямую).
- **По умолчанию Remnawave 3 отдаёт нашему User-Agent ссылки base64**, а
  полный JSON — только если в панели включено «Serve JSON at base
  subscription» (по умолчанию выключено) или задано правило ответа. В
  ссылках нет `mux`. `CLAUDE.md` раньше утверждал обратное — исправлено.
- base64: 5 узлов с флагами-картинками, срок «истекает через 436 дней»,
  `Profile-Title` подставился в имя; пинг всех пяти типов проходит; TUN
  через REALITY работает, `curl.exe` из своего профиля уходит на узел.
- JSON: сохраняются обе копии (конфиги провайдера и отдельные узлы), `mux`
  WS-узла на месте; переключение на «Конфигурацию провайдера» без
  скачивания, строки с меткой Remnawave, без пинга и выбора по одному.
- конфиг провайдера в TUN: ядро поднялось, 10808/10809 провайдера не
  открылись, трафик идёт по правилам шаблона: по журналу ноды через неё
  прошёл только нужный домен, блок из шаблона ответил 403, домены
  «напрямую» на ноду не попали.
- не проверены: kill switch и режим системного прокси на конфиге
  провайдера, «Скопировать в личный Raw», частичный импорт (#229).
- для стенда: цель REALITY `www.microsoft.com` сейчас не работает даже
  между двумя Xray 26 (рукопожатие не проходит), `www.apple.com` и
  `dl.google.com` работают. Это свойство конфига провайдера, не
  приложения.

**User-Agent подписок** (#229): все загрузки шлют
`v2rayN/0.1.0-beta.7 HyperClient/0.1.0-beta.7 (...)`. Проверено 21.10 на
подписке HYPER VPN: на старый и новый User-Agent панель отдаёт одни и те
же 12 ссылок (vless, trojan, hysteria2, awg, mw) с теми же именами, JSON
не приходит; `Profile-Title` подставляется в имя новой подписки. INCY и
другие провайдеры не проверены (их подписок нет в базе приложения).

**Маршрутизация из #220**: `leastPing` проверен в виртуалке (2 входных
узла, проверка раз в 30 с): когда один путь в «Сбое», запросы идут через
живой без ошибок; запасной выход — первый узел, не `direct`. Индикатор
«Цепочки подключения» на главной в нашей вёрстке выглядит нормально;
флаг в нём печатался буквами «NL» — исправлено, теперь картинка Twemoji.
Не проверены отдельно списки DNS-серверов по правилам и настройки sniffing.

**«Набор номера сервера»** (#230): «IPv4 + IPv6» с Happy Eyeballs в TUN
подключается, впереди стоят `app-dns-bootstrap`, переподключение под kill
switch проходит. IPv6 на интерфейсе виртуалки выключен, так что сам Happy
Eyeballs не выбирал между семействами; смену узла при этом не проверял.

**Живая смена узла** проверена на настоящем ядре: обычный узел → обычный
узел без UAC («switched live», то же ядро), с профилями (правила с
`ext:ru-blocked-*.dat` `controlXray` собирает в процессе приложения);
minewire ↔ обычный — перезапуск с UAC, как и задумано.

**Внешний вид**: кнопка маршрутизации на телефоне, кнопка сортировки и
кнопки справки (#221) отдельно не смотрел. На экране 1024×768 диалог
добавления подписки не помещается: кнопку видно только после прокрутки.

**Сборка**: релизная сборка установщика была сломана слиянием #228
(скрипт звал `dart run ffigen`, генерация переехала в `tool/ffigen.dart`);
исправлено, установщик собран, поставлен в виртуалку и удалён ею.
Мобильные и macOS-части апстрима (бэкапы Apple, Android) форк не собирает.

### TUN на хосте 22.10: нет интернета в «Выборочно»

Владелец проверял beta.8 на своей машине: режим «Выборочно», включён один
профиль «Нейросети», kill switch выключен. В TUN «нет ни интернета, ни
пинга», в режиме системного прокси «пропускает всё». Разобраны
`run/error.log` и `run/app.log` за сессии 02:01–02:14 и сеть хоста.

- **Причина в TUN — собственный DNS ядра.** В TUN ядро запускается с
  `-dns <DNS туннеля IPv4>:53 -interface Ethernet` (по умолчанию 8.8.8.8),
  и libXray (`dns.SetDNS`) ставит процессу резолвер Go, который на каждый
  запрос открывает новый UDP-сокет к этому серверу. Через него идут домены
  прямых соединений: sniffing с `routeOnly: false` подменяет адрес на
  домен, и `freedom` разрешает его заново (`net.DefaultResolver`, ещё до
  набора — ради `finalRules`). Через него же разрешаются домены серверов
  узлов.
- **С сети владельца 8.8.8.8 по UDP теряет 20–30% запросов со свежих
  сокетов.** Замер без TUN: 18–25 потерь из 80. Через один сокет — 0 из 80;
  8.8.4.4, 1.1.1.1 и 77.88.8.8 — 0 из 40; TCP к 8.8.8.8 — 0 из 40; роутер —
  3 из 40. Похоже на фильтр провайдера на новые потоки к 8.8.8.8.
- Резолвер Go ждёт 5 секунд на каждую потерю, а соединения к тому же хосту
  ждут тот же запрос. От `dialing TCP` до `connection opened` у прямых
  соединений: в режиме прокси медиана 0,02 с; в TUN медиана 2,8 с, 41 из
  100 — дольше 4 с (5, 7, 10, 12 с). В первой сессии за 16 секунд не
  открылось ни одно из 15 соединений.
- Внутренний DNS Xray (системные запросы через туннель → `dnsOut`) ходит на
  тот же 8.8.8.8, но через один сокет, и отвечал за 20–40 мс.
- В «Выборочно» напрямую идёт почти всё, поэтому TUN выглядит мёртвым. В
  умном режиме большая часть трафика уходит на узел по домену, и задержка
  заметна меньше. Возможно, та же причина у «no connection after 3 probes»
  в TUN 21.10.
- Первые запросы через DNS узла (`app-dns-proxy`, UDP через VLESS XHTTP)
  отвечали за 5–10 с — отдельная медленная часть, только в начале сессии.
- **Режим прокси работает по настройкам.** Через узел шли домены
  «Нейросетей» (`api.anthropic.com`, `claude.ai`) и программы профиля
  (`claude.exe`), остальное (Discord, Яндекс, Microsoft) — напрямую. Прямые
  соединения там разрешает системный резолвер: 20 мс.
- **Проверка связи в «Выборочно» меряет прямой путь.** `LivePingProbe` и
  монитор здоровья ходят на `cp.cloudflare.com` и `www.gstatic.com`; ни один
  профиль их не называет, и они уходят по `app-selective-direct`. В режиме
  прокси «пинг» на главной — задержка прямого интернета, а неработающий
  узел монитор не заметит. В TUN проба попадает на тот же медленный DNS
  ядра (таймаут пробы 8 с).
- Не причина, а шум: `failed to set IPV6_UNICAST_IF` на каждом прямом
  наборе (уровень Info, IPv4-соединение открывается) и отказы IPv6

### Гонка записи на сервере minewire

У сервера автора (v26.7.3) та же ошибка, что была в клиенте: кадр уходит

### Задержка minewire под нагрузкой

Под параллельной закачкой пинг через minewire растёт до 1–2 с: клиент
разрешает серверу до 16 МБ в полёте на поток (`MaxStreamWindowSize`,
`third_party/minewire-cli/src/core/tunnel.go`), и интерактивные запросы
ждут в общей очереди одного TCP. Окно ограничивает только направление
сервер → клиент, минимум yamux 256 КБ, совместимость протокола не
меняется. Подобрать (1–2 МБ хватает на ~300 Мбит/с при 50 мс) и замерить
на стенде: закачка через движок и пинг рядом.

[cacggghp/vk-turn-proxy](https://github.com/cacggghp/vk-turn-proxy)

AmneziaWG из пункта 3). «Тонкая поддержка» в интерфейсе: ссылка на звонок,
адрес сервера, число потоков, TCP или UDP до TURN, диалог капчи.

завершён. Оценка: крупная; логично после пункта 3.

### 5. Отчёт о сети для ВПНщиков (первая часть сделана 25.10.2026)

Сделано: libXray `netreport` и экраны «Отчёт о сети» и «Данные отчёта».
Отчёт различает подмену DNS (инъекция, поддельный NXDOMAIN, заглушка,
перехват, потери), блокировку по адресу, по имени, белый список имён на
диапазоне адресов, «только без SNI», заморозку после ~16 КБ, гео-блок
самого сервиса и два режима белых списков: по адресам (вне разрешённых
сетей не отвечает ничего, даже VPN-сервер; помогает только посредник в
разрешённой сети) и по именам (адреса отвечают, DPI пропускает только
разрешённые SNI; проходят REALITY с таким именем и Fragment). Разделение —
замечание владельца 25.10: «белые списки» в общем смысле — это блок по IP
всего неразрешённого. Обход DPI проверяется без запуска zapret: закрытые
сайты и хостинги повторяются с ClientHello, разрезанным на два TCP-пакета
и, как делает Fragment в приложении, на TLS-записи по 100–200 байт, и
засчитываются, только если после рукопожатия прошли и данные; проверяет хостинги VPN (Hetzner DE/
FI/US, OVH, Vultr, Scaleway, Gcore, Google Cloud, AWS, Cloudflare,
Selectel, Yandex Cloud) со своим и с разрешённым именем, какие имена SNI
пропускаются, UDP (STUN) и QUIC. Вывод «что подойдёт» строится только из
замеров и называет хостинги и имена, на которых он основан.

Замеры 25.10 (сеть владельца и телефон по USB):
- ДОМ.RU (AS31363): инъекция DNS-ответов на пути к любым публичным
  резолверам (заглушка за 2 мс, настоящий ответ следом), 8.8.8.8 теряет
  20–25% запросов; Instagram, Telegram, WhatsApp — по адресу; TLS с любым
  именем к Hetzner DE/FI, OVH, Vultr AMS режется, без имени проходит;
  Hetzner US, Scaleway, Gcore, Google Cloud открыты.
- ДОМ.RU, обход DPI: два TCP-пакета не помогают нигде; Fragment открывает
  TikTok, OVH, Vultr AMS и AWS, Hetzner DE/FI — нет.
- МегаФон (AS25159), USB-модем: белый список имён, не адресов (адреса
  Google, Cloudflare, Hetzner US отвечают). 8.8.8.8 и 1.1.1.1 отвечают
  поддельным NXDOMAIN с флагом AA, Quad9 честный. С чужими адресами
  проходят только SNI `ya.ru` и `mail.ru` (vk.com, Госуслуги — нет); с
  `ya.ru` Hetzner US, Google Cloud и Selectel отдают 256 КБ целиком, Hetzner
  DE/FI, OVH, Scaleway, Gcore закрыты по адресу. QUIC до Google и YouTube
  проходит, хотя TLS к ним режется; STUN Google отвечает, Cloudflare нет.
  Fragment открывает 16 закрытых сайтов с данными (YouTube, Google,
  GitHub, Gemini, ChatGPT, Claude, Wikipedia…) и хостинги Google Cloud,
  AWS, Selectel; два TCP-пакета — ничего. Результаты меняются между
  прогонами.

Дальше, по шагам:
- **Свои узлы**: рукопожатие и передача 256 КБ через каждый узел
  пользователя его протоколом (инфраструктура `pingBatch`: временный Xray
  в процессе приложения), параллельные соединения («сибирское»
  ограничение), узел — протокол и хостинг, без адресов.
- **Телефон**: пускать пробы мимо работающего VPN (`VpnService.protect`)
  вместо просьбы отключить его; передавать системные DNS сети (`systemDns`)
  с Android.
- **Обход DPI**: сделана проверка того, что умеет само приложение
  (Fragment). Приёмы zapret на уровне пакетов не проверяются: им нужны
  драйвер и права администратора.
- **Просмотр на сайте**: отчёт в части ссылки после `#`, страница на сайте
  проекта рисует ту же сводку.
- **Проверочный сервер ВПНщика**: эхо TCP/UDP на его же сетях, чтобы
  проверить сигнатуры WireGuard/OpenVPN/QUIC и заморозку на его адресах.
- IPv6 и MTU пути; повтор неустойчивых проверок.

### 6. DNS узла (AmneziaWG сделано 24.10.2026)

Сделано для AmneziaWG: один выбранный узел без финального выхода
разрешает имена через DNS своего конфига, если DNS для VPN в настройках
не менялся (`ConnectionCompiler._withNodeDns`, `CLAUDE.md`). Уточнение к
плану ниже: сам выход `amneziawg` в libXray `remoteDNS` уже использовал —
его сетевой стек разрешает домены назначения внутри туннеля. Правка
добавила собственный DNS Xray (`app-dns-proxy`: системные запросы в TUN,
правила по IP), который ходил на 8.8.8.8. Проверено на настоящем ядре с
узлом HYPER VPN: запросы ушли на `172.29.172.254` (AmneziaDNS, с 24.10 —
unbound на хосте) через туннель. TUN целиком и смена узлов в приложении
не проверены. Осталось: произвольный DNS у любого узла (поле в узле и
подписке, интерфейс), если понадобится.

Идея владельца 24.10.2026: подключение использует DNS своего узла
(резолвер хостера или собственный unbound на VPS, как AmneziaDNS), а не
общий `app-dns-proxy` (8.8.8.8 через туннель).

- **Узлы-прокси** (VLESS, Trojan, Hysteria2, minewire) с FakeDNS уже
  разрешают сайты на выходе: ядро отдаёт серверу имя, адрес ищет сервер.
  8.8.8.8 нужен только без FakeDNS, для правил по IP и запросов самого
  ядра.
- **AmneziaWG** работает пакетами IP: имя на сервер не уходит, его
  разрешает клиент. Строка `DNS =` конфига хранится при импорте
  (`remoteDNS`, `lib/service/amneziawg/conf.dart`).

План: когда выбран один узел AmneziaWG со своим DNS, `app-dns-proxy`
берёт этот DNS и ходит только через этот узел, без запасного (адрес
вроде `172.29.172.254` доступен лишь внутри своего туннеля). Остальное —
как сейчас.

Ловушки:
- DNS не входит в `LiveControl.swappable`: смена узла с другим DNS станет
  перезапуском (в TUN — запрос UAC). Можно менять DNS только при
  перезапуске и не трогать при живой смене.
- Автовыбор и балансировщик из нескольких узлов: один DNS узла не выбрать,
  остаётся общий.
- Узел VLESS на том же VPS дотянется до внутреннего DNS, только если
  маршрутизация Xray на сервере не блокирует приватные адреса (шаблон
  x-ui часто блокирует `geoip:private`).

Оценка: небольшая для AmneziaWG, средняя для произвольного DNS у любого
узла (поле в узле и подписке, интерфейс).
